# gadget-monitor

Monitoring for the `arnor` and `gondor` JupyterHub/compute hosts on UW DiRAC
infrastructure. Small check scripts run on the targets over persistent SSH
sessions every 5 minutes; results go into VictoriaMetrics and are graphed in
Grafana. Everything runs in containers on one VM and deploys with:

```bash
sudo ./init.sh
podman compose up -d --build
```

The dashboards are at the VM's URL (the VM's reverse proxy terminates TLS and
forwards to `127.0.0.1:8080`). Anyone can view; there is one `admin` account
whose password is on shire (see `SECRETS.md`).

## How it works

```
 arnor, gondor                      this VM (podman compose)
 ┌──────────────┐   one SSH session   ┌───────────┐  import  ┌─────────────────┐
 │ remote agent │◄═══════════════════►│ collector ├─────────►│ victoriametrics │◄── grafana :8080
 │ (python3)    │   per host, kept    └───────────┘          └────────▲────────┘
 └──────────────┘   open; checks sent                          snapshot │
                    each cycle                                 ┌────────┴─┐
                                                               │  backup  ├──► /service/shire
                                                               └──────────┘
```

- The **collector** keeps one SSH session per host open permanently. The
  session runs a small Python **agent** (`agent/agent.py`), sent over stdin at
  connect time, so nothing is installed on the targets. Each cycle the
  collector sends the due check scripts to the agent, which runs them with a
  timeout and returns their output. A normal cycle opens no new SSH
  connection and never touches the NFS home directory on the targets.
- **VictoriaMetrics** stores the data on the VM's local disk
  (`/local/gadget-monitor`) for 100 days.
- **Backups** go to `/service/shire/gadget-monitor/backup` every hour (plus a
  daily copy), and `init.sh` restores from them on a new VM.
- **Grafana** has a provisioned "Hosts overview" dashboard.

## Adding a check

A check is one file in `checks/`. It runs on every host in
`config/hosts.toml`, unless the check has a `# hosts:` line (then only on
those hosts) or a host lists its `checks` explicitly.

```bash
#!/bin/bash
# interval: 300
# timeout: 30
# hosts: gondor          (optional; omit to run on every host)
# One-line description of what this measures.
awk '...' /proc/something
```

Rules:

1. **Print Prometheus text format** on stdout: `metric_name{label="value"} 123`,
   one sample per line. Comments (`#`) and blank lines are ignored. Do not
   print timestamps; the agent records when the check started.
2. **Don't set `host` or `check` labels.** The collector adds them, and drops
   lines that try.
3. **Never use unbounded values as labels**: no PIDs, job or session IDs, or
   usernames that come and go. Every distinct label combination is a new
   series stored for 100 days, and series count is the main threat to the
   size budget. More than 500 lines per run are dropped.
4. **Be cheap and safe on a struggling host.** Prefer reading `/proc` and
   `/sys` to running tools. Don't touch NFS unless that is what the check is
   testing, and then give it a short timeout. Checks run unprivileged as
   astro-gadget, from `/`, with a minimal environment (`PATH`, `LC_ALL=C`).
5. **Exit 0** on success. A non-zero exit is recorded as an error and the
   output is discarded.
6. **Use the counter pattern for rates.** Report raw counters (like
   `gadget_cpu_seconds_total`) and compute rates in Grafana, rather than
   sampling twice inside the check.
7. **Name things consistently.** Use the `node_exporter` name when the meaning
   is identical (`node_load1`); otherwise prefix with `gadget_` and put the
   unit in the name (`_bytes`, `_seconds`, `_total` for counters).

To try a check by hand from the VM:

```bash
podman exec -i gadget-monitor-collector ssh -T -F /dev/null -i /dev/shm/gadget-ssh-key \
    -o UserKnownHostsFile=/srv/config/known_hosts \
    astro-gadget@arnor.astro.washington.edu 'bash -s' < checks/mycheck.sh
```

Then rebuild the collector (see "Updating" in `DEPLOY.md`) and add a panel.
The dashboard is generated by `grafana/gen_hosts_overview.py`. Edit that and
regenerate the JSON, or build the panel in the UI, export it, and fold it
back into the generator.

## Current checks

| Check | Metrics |
|---|---|
| `cpu` | `gadget_cpu_seconds_total{mode}` (all cores combined), `gadget_cpu_count` |
| `load` | `node_load1`, `node_load5`, `node_load15` |
| `memory` | `node_memory_{MemTotal,MemFree,MemAvailable,SwapTotal,SwapFree}_bytes` |
| `gpu` (gondor only, every minute) | `gadget_gpu_memory_{total,free}_bytes{gpu}`, `gadget_gpu_utilization_percent{gpu}`, `gadget_gpu_utilization_max_percent{gpu}`, `gadget_gpu_processes{gpu}` |
| `nfs` | `gadget_nfs_{ops,queue_seconds,rtt_seconds,execute_seconds}_total{fs,op}`, `gadget_nfs_volumes{fs}` |

**`gpu`** makes one `nvidia-smi -q` call. GPU utilization is bursty and the
driver keeps no cumulative busy counter, so the check reports the average and
peak of the driver's own samples over the ~14 s before each run; running every
minute covers about a quarter of the time. Memory-bandwidth utilization,
power, temperature, throttling and ECC are available from the same call but
deliberately not collected.

**`nfs`** reads the kernel's NFS client counters from `/proc/self/mountstats`
(cumulative since mount; reading them never touches the network). `fs` is
`helios` (every helios mount summed: home directories and apps share one
filesystem), `shire` or `shiren` (separate storage on the same server). Other
NFS servers are ignored. Mounts sharing a superblock report identical
numbers, so each superblock is counted once; `gadget_nfs_volumes` is how many
were summed. `op` is READ, WRITE, GETATTR, LOOKUP, ACCESS, OPEN (including
OPEN_NOATTR), CLOSE or OTHER. Times:
- `queue`: waiting in the client before the call was sent;
- `rtt`: sent until the reply arrived;
- `execute`: the whole call.

Average per call over an interval is `rate(..._seconds_total) / rate(gadget_nfs_ops_total)`.
A call is only counted when it finishes, so a hung server shows as a gap in
these graphs rather than a spike.

**Login probe** (built into the collector, not a file in `checks/`): every
5 minutes, and every 15 after repeated timeouts, the collector opens a
brand-new interactive SSH login to each host. It types a command and times
how long the login takes to become usable. The results are
`gadget_ssh_login_seconds{stage}` with stages `connect` (DNS and TCP), `auth`
(key exchange and authentication; this reads `authorized_keys` from the NFS
home directory), `shell` (session, login shell and profile until the command
runs) and `total`. A login that hangs records only the stages it finished,
and shows as `check="ssh_login"` timing out after 60 s.

The collector also records, for every host and check (including `ssh_login`):
- `gadget_check_success`;
- `gadget_check_status{status}`, where status is ok, error, timeout,
  skipped_running, unreachable or lost;
- `gadget_check_duration_seconds`;
- `gadget_check_lines_{emitted,dropped}`.

And for every host:
- `gadget_ssh_connected`;
- `gadget_ssh_reconnects_total`;
- `gadget_clock_skew_seconds`.

The backup container records `gadget_backup_*` and `gadget_storage_bytes`.

## Local development

`dev-startup.sh` runs the stack with Docker on a laptop, keeping state under
`./dev-data/`. Without a copy of the SSH key in `dev-data/ssh-key`, the
collector just reports both hosts as unreachable. That is still enough to
work on dashboards and the backup scripts.
